# Git Squash Rules for ios-memories-nextcloud

## ⚡ Règles de Commit

### 1. **Un commit = Une fonctionnalité**
- **Toujours** squasher les commits feature + tests en UN SEUL commit
- **Jamais** de commits séparés pour la feature et ses tests

### 2. **Message de commit**
- Utiliser le format : `type: description`
- Exemples : `fix:`, `feat:`, `chore:`, `test:`
- Inclure la référence à l'issue : `Fixes #X` ou `Resolves #X`

---

## 🎯 Alias Git Disponibles

### Squasher les 2 derniers commits (feature + test)
```bash
git squash-last
```

Ce que ça fait :
1. `git reset --soft HEAD~2` - Annule les 2 derniers commits mais garde les changements
2. `git commit --amend` - Crée un nouveau commit avec tous les changements

### Squasher avec un message personnalisé
```bash
git squash-last -m "fix: your message here"
```

---

## 🛑 Règles pour les Agents

**INTERDIT** :
- ❌ Pousser automatiquement après un commit
- ❌ Créer des commits séparés pour feature et tests

**OBLIGATOIRE** :
- ✅ Attendre validation avant de pousser
- ✅ Squasher feature + tests en un commit
- ✅ Utiliser un message de commit clair et descriptif

---

## 📋 Workflow Recommandé

### Pour une nouvelle fonctionnalité/fix :

1. **Travailler** sur la feature
   ```bash
   git checkout -b feature/fix-issue-X
   ```

2. **Implémenter** la solution
   ```bash
   git add .
   git commit -m "feat/fix: description"
   ```

3. **Ajouter les tests**
   ```bash
   git add Tests/
   git commit -m "test: add tests for feature"
   ```

4. **Squasher** les commits
   ```bash
   git squash-last -m "fix: complete description including tests. Fixes #X"
   ```

5. **Pousser** (après validation)
   ```bash
   git push origin feature/fix-issue-X
   ```

## 🔧 Configuration

Ces règles sont configurées dans :
- `.git/config` (alias locaux)
- `.git-squash-rules.md` (ce fichier)

Pour appliquer les alias globalement :
```bash
git config --global alias.squash-last '!f() { git reset --soft HEAD~2 && git commit --amend; }; f'
```

---

## 💡 Bonnes Pratiques

- **1 commit = 1 PR** : Une pull request doit contenir un seul commit (sauf si c'est une série logique)
- **Messages clairs** : Un bon message de commit explique le QUOI et le POURQUOI
- **Tests inclus** : Toute nouvelle fonctionnalité doit avoir ses tests dans le même commit
- **Validation** : Toujours tester localement avant de pousser

## 📚 Exemples

### ❌ MAUVAIS
```bash
# Commit 1
git commit -m "fix: share link issue"

# Commit 2 (séparé)
git commit -m "test: add share link tests"

# Push sans squash
git push
```

### ✅ BON
```bash
# Commit 1
git commit -m "fix: share link issue"

# Commit 2 (séparé)
git commit -m "test: add share link tests"

# Squash avant push
git squash-last -m "fix: use real server URL for public share links. Fixes #7"

# Push après validation
git push
```
